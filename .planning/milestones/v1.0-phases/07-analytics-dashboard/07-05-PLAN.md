NF3.4 requires a `company_id + platform + status` compound index. PostVariant has `platform` and `status` but no direct `companyId` column (companyId lives on ContentPost via the `post` relation). Dashboard queries filter `post: { companyId }` which becomes a JOIN — the compound index cannot exist without a direct column.

Follow the PostMetrics denormalization pattern (PostMetrics already has a denormalized `companyId`):

1. In `libraries/nestjs-libraries/src/database/prisma/schema.prisma`, update the PostVariant model:
   - Add `companyId String?` field (nullable to avoid breaking existing rows — backfill will populate)
   - Add `company Company? @relation(fields: [companyId], references: [id], onDelete: Cascade)` relation
   - Add `@@index([companyId, platform, status])` compound index (NF3.4)
   - Keep all existing indexes unchanged

   IMPORTANT: Check if Company model already has a `PostVariant` relation. If not, you may need to add `postVariants PostVariant[]` to the Company model. Also check if Company already has the maximum number of relations — Prisma allows multiple relations from different models to the same model.

2. Create migration directory and SQL file at `libraries/nestjs-libraries/src/database/prisma/migrations/20260311100000_postvariant_companyid_index/migration.sql`:
   ```sql
   -- Add denormalized companyId to PostVariant for NF3.4 compound index
   ALTER TABLE "PostVariant" ADD COLUMN "companyId" TEXT;

   -- Backfill companyId from ContentPost
   UPDATE "PostVariant" pv
   SET "companyId" = cp."companyId"
   FROM "ContentPost" cp
   WHERE pv."postId" = cp."id";

   -- Add FK constraint
   ALTER TABLE "PostVariant" ADD CONSTRAINT "PostVariant_companyId_fkey"
   FOREIGN KEY ("companyId") REFERENCES "Company"("id") ON DELETE CASCADE ON UPDATE CASCADE;

   -- NF3.4: compound index on company_id + platform + status
   CREATE INDEX "PostVariant_companyId_platform_status_idx" ON "PostVariant"("companyId", "platform", "status");
   ```

   NOTE: companyId is nullable in schema because existing rows need backfill. The UPDATE statement populates all existing rows. New PostVariant rows should have companyId set by the application code, but that is a future concern (Phase 6 ContentPostService sets postId, and companyId can be derived from ContentPost at insert time). For the index to be most effective, the backfill is critical.
